## Game concept

The game is built on two-part design terms. The player sees a **main word** (e.g. WIRE) and must guess a **connecting word** that forms a real design term with it (WIRE + FRAME = WIREFRAME). Terms may be one word (wireframe) or two words (drop shadow).

The connecting word is shown as its first letter followed by dashes for the remaining letters (`F _ _ _ _`). When correct, the connecting word becomes the new main word and a new hint appears (FRAME → `W _ _ _` = FRAMEWORK). The chain continues endlessly, getting harder.

## Dataset API

`design-terms.js` is loaded with a normal `<script>` tag.

- Each term object: `{ rank, difficulty: "easy" | "moderate" | "hard", first, second, term, category, definition }`
- `getNextRound(mainWord, round, usedSet)` returns the term for the next round.
  - `round` = number of correct answers so far + 1
  - Pass `null` as `mainWord` at game start.
  - Add each played term's `term` string to `usedSet`.
  - If the returned object has `newChain: true`, show a brief "New chain!" message and display `term.first` as the new main word.
  - Difficulty ramps automatically: rounds 1–3 easy, then a moderate/hard mix that gets harder.
- `checkGuess(target, guess)` returns the matching term object or `null`. It is case-, space- and hyphen-insensitive and may accept an alternative valid term with the same first letter and length. If it returns a different term than the target, use the **returned** term (its `second` becomes the next main word, and it goes into the chain history).

## Rules

- 30-second timer per word, resetting after each correct answer.
- Correct: +10 points plus a speed bonus of 1 point per second remaining.
- Wrong: lose 1 of 3 tries. Tries reset to 3 after each correct answer.
- Game over when: 3 wrong tries on the same word, **or** the timer reaches zero.
- Save the best score in `localStorage` (wrapped in try/catch).

## Phase 1 — Core game (no camera)

Build the complete playable game with the word card centered on screen.

1. **Start screen:** title "Design Chain", a one-line explanation with a small animated example (WIRE + FRAME → WIREFRAME), best score, and a "Play" button.
2. **Game screen:**
   - Word card in the center. Line 1: main word, large and bold. Line 2: the guess word as letter slots: first letter pre-filled and highlighted, then one empty slot/dash per remaining letter.
   - As the player types, letters fill the slots left to right with a small pop animation; backspace clears them in reverse. The first letter is locked. Input is capped at the word length.
   - A text input bar pinned to the bottom of the screen (auto-focused, Enter submits). Mirror typed letters into the slots live. The input accepts the full second word; the first letter in the slots is just a hint.
   - Small difficulty tag on the card: Easy / Moderate / Hard.
   - HUD at top: score, chain length, 3-tries indicator, circular 30-second timer ring.
3. **Feedback:** correct → card turns green with a glow, the two parts merge into the full term (e.g. WIREFRAME or DROP SHADOW, using `term.term`), then transitions to the next round. Wrong → card turns red and shakes, slots clear except the first letter.
4. **Game over screen:** final score, longest chain, best score, "Play again", and "Copy result" (copies a short emoji summary). Below, a scrollable vertical list of term cards for every completed term in order, each showing the term and its definition. Add a final card labeled "Missed" with a soft red accent showing the term the player failed, with its definition. Keep the buttons always reachable.
5. **Mobile:** the input and word card stay visible above the on-screen keyboard; large tap targets.

Several browsers end a continuous session more eagerly when interim results are off; keeping them on tends to keep the underlying session alive longer between restarts. **Honest caveat: this part is a well-reasoned but unverified attempt** — real `SpeechRecognition` audio/restart behavior can't be exercised in this sandboxed environment (no microphone), so whether it measurably reduces the clicking needs a real-device check.
  - **"Still not taking the words properly" — a real, concrete bug found and fixed.** Chrome's `SpeechRecognition` treats recognized phrases like sentences: it commonly capitalizes the first letter and appends trailing punctuation (e.g. saying "wireframe" can come back as `"Wireframe."`). Both matching paths — `checkGuess()` in `design-terms.js` and `normalizeForMatch()` in `game.js` — only ever stripped whitespace and hyphens, never other punctuation, so a transcript like `"Wireframe."` would *never* match `"wireframe"` after lowercasing, for either the connecting-word check or the full-term fallback. This is very likely the dominant real cause behind both this report and the earlier "not taking my responses"/"hanging" reports, which were investigated and partially fixed without catching this specific root cause. Fixed in `ui.js`, not the matching logic itself: a new `sanitizeVoiceTranscript()` strips everything except word characters, whitespace, and hyphens (`.replace(/[^\w\s-]/g, "")`) from every voice transcript *before* it's ever used for matching, in `handleVoiceResult()` — scoped to voice specifically (typed input never has stray punctuation, so it doesn't need or get this treatment). Verified live with transcripts shaped exactly like real Chrome output: `"View."` correctly resolved to `correct` against a connecting-word target, and `"Viewport."` correctly resolved to `correct` via the full-term fallback — neither would have matched before this fix. Re-ran the Node regression (30 games, zero chain breaks) and confirmed no console errors; **this fix is also included in the Vercel deployment above, pushed as part of the same update** (see the redeploy note below).
- **Voice answers now fill the letter slots live, same as typing** ("fill the letters of the word that is taken as response, so the user know which word is wrong or right and user can guess the direction of the word"). Previously the slots only ever reflected typed input — a spoken guess went straight from silence to a plain correct/wrong card color with no letter-level view in between. `ui.js`'s `handleVoiceResult()` now calls `buildSlots(activeSecondWord, heardSoFar)` with the accumulated (sanitized) transcript every time a new fragment arrives, exactly like the existing `input` event listener does for typing — the locked first letter stays as the hint, and whatever's been heard fills the remaining slots, letter by letter, so the player can see which letters are landing right or wrong and judge how close the guess is. This only updates the letters, not the card's color/state, so it doesn't reintroduce the premature-wrong-flash problem fixed earlier — the card still only turns red or green once a guess is actually resolved (an immediate match, or the debounce elapsing). Also switched the debounced fallback's fragment join from `" "` (space) to `""` (direct concatenation) to match how the slots represent a single word's letters one per box; this has no effect on matching, since `checkGuess()`/`normalizeForMatch()` strip whitespace either way. Verified live: speaking a wrong word ("cat" against target "out") immediately showed `O-A-T` in the slots (locked correct first letter + the heard letters) while the card stayed neutral (no premature wrong state, tries untouched) until the debounce resolved it to wrong; speaking the correct word showed the fully correct `O-U-T` right before the card turned green and merged. No console errors; Node regression still clean.
- **Follow-up ("for correct answers as well fill up the letters in the blank. try again") — the slots fix above wasn't actually visible for correct answers, found and fixed.** The slots genuinely were being filled with the complete correct word first — confirmed in the previous verification — but `handleCorrectFeedback()` applied `.word-card.correct` in the very same synchronous step, and that class hides `.card-slots`/shows `.card-merged` via a hard CSS `display` swap with no transition. So the filled-in slots and the merged green state landed in the same paint frame — the completed word was never actually visible to the player before being replaced, especially noticeable for voice since the player doesn't control the reveal pace the way typing does. Fixed in `ui.js`: a new `CORRECT_SLOT_REVEAL_MS` (400ms) delay now sits between a correct guess and applying `.correct`/the merged text — the fully-filled slots are shown for that brief pause first, then it merges into the green state as before (the existing `CORRECT_ANIM_MS` celebratory duration afterward is unchanged, just pushed back by the reveal delay; `proceedToNextRound()` now fires after `CORRECT_SLOT_REVEAL_MS + CORRECT_ANIM_MS`). Applies equally to typed and voice input, since both share this one function. Verified live for both: immediately after a correct guess (voice: "line" → target "line"; typed: "out" → target "out"), the slots showed the complete word (`L-I-N-E`, `O-U-T`) while `.correct` was confirmed *not yet* applied, then after the reveal delay it correctly merged and turned green. No console errors; Node regression still clean (this change is pure `ui.js` timing, `game.js` untouched).
